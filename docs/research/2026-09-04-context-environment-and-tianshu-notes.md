# 长程 Agent 上下文管理调研笔记

日期：2026-09-04

## 一、Tianshu 与 LANTU

LANTU 已有固定 System Prompt、标准工具模式、工具结果控制、File Ledger、结构化压缩和 Session Journal。Tianshu 的主要优势不只是缓存机制，而是把缓存失效、压缩成本和运行行为做成了可复核的观测数据。

### Tianshu 值得借鉴的内容

1. **双层请求指纹**

   在上下文组装完成时记录一次指纹，在 Client 真正发送前再记录一次指纹。这样可以区分：

   - Agent 组装上下文时已经变化；
   - Client 发送前修改了请求；
   - 两层都稳定，但服务商没有命中。

2. **所有模型调用统一记账**

   主请求、压缩摘要、记忆提取、子 Agent 和其他 side-path 都单独记录，避免辅助请求产生成本盲区。

3. **压缩成本归因**

   记录压缩前后 Token、实际回收量、摘要请求成本，以及压缩后恢复到高命中率所需的请求数。

4. **行为门禁**

   通过简单规则检测重复失败调用、修改代码后未验证、没有证据就交付等问题。LANTU 不需要复制完整 CVM，只需优先实现重复调用检测和验证债务。

5. **缓存回归测试**

   对 System Prompt、工具 Schema、消息序列化、Hook、压缩和 Client 建立前缀稳定性测试。

## 二、动态 Appendix

Appendix 是放在用户消息或上下文末尾的动态运行状态，例如当前分支、Git 状态、任务进度和验证状态。

推荐结构：

```text
固定 System Prompt
固定工具 Schema
历史消息
用户消息
<context-update>
  发生变化的运行状态
</context-update>
```

Tianshu 将动态状态拆成多个块。只有发生变化的块才重新追加，没变化的块不重复发送；数值型状态还会分桶，避免无意义的小数变化破坏字节前缀。

LANTU 当前通过 `system-reminder` 和 `reminder_key/reminder_hash` 去重，思想相近但粒度更粗。是否引入完整 Appendix 状态机，应先通过请求指纹确认 reminder 是否是主要未命中来源。

## 三、历史边界冻结

一次真实用户消息及其当时的附加内容组成一个历史边界。历史边界一旦真正发送，就不应因为后续 Git 状态、Hook 或进度变化而重新构造。

错误方式：

```text
第一次：用户消息 + Git 干净
下一次：同一用户消息 + Git 有修改
```

这样会从该历史位置开始破坏缓存前缀。

正确方式：

```text
历史用户消息冻结为第一次实际发送的字节
最新 Git 状态只追加到当前对话末尾
```

Tianshu 还把冻结快照持久化，恢复 Session 后继续使用相同内容。LANTU 的 reminder 已经写入 Conversation 和 Journal，历史通常不会重新生成；是否需要额外冻结文件，应由指纹测试决定。

## 四、CVM：认知虚拟机

CVM 是 Agent Loop 外部的行为监督层，不是操作系统虚拟机，也不是另一个模型。它在模型请求前、模型输出后、工具执行后和任务结束时检查行为。

```text
模型准备行动
    ↓
规则与状态检查
    ↓
允许、提醒、阻止或要求验证
    ↓
工具执行
    ↓
结果检查并更新状态
```

典型规则：

- 相同失败命令连续执行；
- 修改文件后没有运行测试；
- 没有证据就宣布任务完成；
- 违反权限或交付规则。

LANTU 的最小可用版本只需要：

```text
最近工具调用指纹
+ 文件修改状态
+ 最近一次验证状态
```

不必实现 Tianshu 的完整 Hook 数量和认知评分体系。

## 五、信息素（Stigmergy）

信息素是附着在文件或路径上的结构化经验信号，用于影响未来任务的读取和修改顺序。

```json
{
  "path": "src/auth/token.py",
  "signal": "fragile",
  "strength": 0.8,
  "evidence": "修改后认证测试失败",
  "half_life": "7d"
}
```

常见信号：

- `fragile`：容易引发回归；
- `well-tested`：刚完成有效验证；
- `dead-end`：某种方案已经失败；
- `entry-point`：关键入口文件。

信息素与 Memory 的区别：

```text
Memory：保存完整经验和事实
信息素：快速提示某个文件当前的风险或价值
```

LANTU 可以基于 File Ledger 和 Journal 做简化版：测试失败后给文件加 `fragile`，测试成功后加 `well-tested`，连续失败方案加 `dead-end`，并使用时间衰减避免过时信息永久影响 Agent。

## 六、Context as an Environment / Scroll

论文的核心观点是：上下文不应被视为必须全部塞进 Prompt 的消息列表，而应被视为一个可查询、可编程的 Session Environment。

Scroll 的结构：

```text
Append-only Event Log
保存全部历史事实
        ↓
持久化、沙箱化 Python Kernel
保存变量和派生状态
        ↓
模型通过 exec 查询和加工
        ↓
只有 print 输出进入下一次工作上下文
```

例如，读取十个文件后不把十个完整结果都塞入上下文，而是保存为变量；模型需要认证相关内容时，用代码筛选并只打印匹配文件和行号。

### 工作视图与完整环境

```text
完整环境：所有消息、工具结果、状态和事件
工作视图：本轮模型真正看到的少量内容
```

工作视图接近上限时，旧内容被移出，但仍保存在 Event Log。Eviction Index 保存主题、文件和精确事件地址，模型以后可以直接找回被移出的片段。

论文报告 Scroll 在 LongMemEval_S、BEAM_10M 和 LOCA_256K 上分别达到 94.8%、73.1% 和 86.7%。这些结果是在特定数据集和 Qwen3.8-Max 上取得，不能直接等价为 Coding Agent 或前缀缓存提升。

## 七、与 LANTU 的关系

LANTU 已经具备 Scroll 的基础形态：

```text
Session Journal：完整事实层
File Ledger：文件版本和可见范围
工具结果落盘：外部结果存储
上下文压缩：构造当前工作视图
```

当前缺少的是精确的历史导航。压缩摘要如果只写“修改了认证模块”，后续可能找不到具体证据；如果同时保存 Journal 序号和 Artifact ID，就可以恢复。

推荐的轻量方案：

```text
Journal 事件索引
    ↓
压缩摘要保存 seq 范围和 Artifact ID
    ↓
当前上下文只保留摘要、近期消息和历史目录
    ↓
RecallSession 按引用读取原始事件
    ↓
召回结果追加到上下文末尾
```

这与 File Ledger 不同：

```text
File Ledger：防止重复读取当前文件，处理文件版本和可见行范围
History Index：防止压缩后找不到历史决策、工具结果和错误细节
```

两个系统都应以 Journal 或磁盘事实为依据，但职责不应合并。

## 八、服务端 Compaction 与“新窗口”

Claude 的服务端 Compaction 返回一个 `compaction` block，后续请求把它原样带回；Block 之前的旧内容由服务端忽略。OpenAI Responses API 的 `/responses/compact` 返回加密、不透明的 `compaction` item，后续请求继续携带它。

这不是简单地删除 Session，而是：

```text
旧完整历史：继续保存
活动上下文：切换为 Compaction Block + 最近消息
```

GLM-5.2 的 OpenAI-Compatible Chat Completions 不能直接使用 OpenAI 的加密 Compaction Item。LANTU 更适合实现“结构化 Checkpoint + Journal 引用 + Recall 工具”。

## 九、短期最值得实现的功能

按收益和复杂度排序：

1. **统一模型请求记账**：主请求、摘要、记忆和子 Agent 分开记录。
2. **双层请求指纹**：定位上下文组装变化还是发送层变化。
3. **历史引用和 RecallSession**：让压缩后的旧细节可恢复。
4. **验证债务规则**：修改文件后未验证，不允许静默完成。
5. **重复失败调用检测**：连续失败时要求改变策略。
6. **缓存回归测试**：验证消息前缀在连续请求中保持稳定。
7. **文件信息素简化版**：从测试结果和失败记录生成短期文件信号。

暂时不建议实现：持久化 Python Kernel、完整 CVM、几十个 Hook、复杂认知评分和大规模信息素图谱。这些功能需要更多安全、恢复和评测工作，短期面试收益不高。

## 十、面试实验方案

### 实验一：确定性前缀稳定性

固定消息和工具调用轨迹，分别关闭和开启缓存相关机制，比较：

- 可复用前缀 Token；
- 未命中输入 Token；
- 压缩后恢复所需请求数；
- 请求指纹首次变化位置。

### 实验二：真实 Coding Agent

保持模型、提示词、权限、思考强度和输出上限一致，运行：

- 20 轮连续代码阅读；
- 2 至 3 个真实代码修改任务；
- 每个配置至少重复 3 次。

记录：任务成功率、整体命中率、稳态命中率、未命中 Token/成功任务、总耗时和请求数。

### 实验三：压缩专项

在固定轮次触发压缩，记录：

```text
压缩前命中率
→ 摘要请求成本
→ 压缩后首次命中率
→ 恢复到 95% 所需请求数
→ 最终任务结果
```

当前 LANTU 已有 GLM-5.2 标准模式的真实结果：整体约 94%，排除首次预热和压缩边界后约 98%。这可以作为现状基线，但要补充统一口径的 A/B，才能证明具体优化的因果效果。

## 十一、面试主线

> LANTU 将上下文拆成固定前缀、可变工作视图和不可变 Session Journal。固定前缀用于稳定缓存，可变内容通过工具结果预算、文件版本去重和尾部压缩控制增长；Journal 保存完整事实，压缩后通过事件引用和按需召回恢复旧细节。后续还可以在 Agent Loop 外增加轻量行为门禁，对重复失败调用和修改后未验证进行实时纠偏，并把结果沉淀为文件级经验信号。
