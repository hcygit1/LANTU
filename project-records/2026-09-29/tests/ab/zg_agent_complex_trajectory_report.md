# ZG 复杂 Agent 轨迹 A/B 测试报告

## 实验设计

- **日期**：2026-09-10
- **模型**：`deepseek-v4-flash`
- **任务**：8 个复杂跨文件代码分析任务
- **重复次数**：每组 3 次，共 48 个任务回合
- **Baseline**：无 MCP，`CodeSearch` 使用本地 `rg`/Python Grep
- **Optimized**：启用本地 zvec-grep MCP，保留相同降级路径
- **一致条件**：任务、顺序、提示、模型、输出上限和权限模式相同

任务覆盖配置到客户端调用链、MCP 装配、File Ledger 生命周期、分级压缩与换窗、工具结果落盘、Schema Epoch、Session 恢复和搜索降级链。

## 汇总结果

| 指标 | Baseline 均值 | ZG 均值 | 变化 |
|---|---:|---:|---:|
| 每轮任务通过 | 7.000/8 | 6.667/8 | -0.333 |
| 总任务通过 | 21/24（87.5%） | 20/24（83.3%） | -4.2 个百分点 |
| 耗时 | 290.253 s | 273.304 s | -5.8% |
| 总工具调用 | 79.333 | 83.333 | +5.0% |
| ReadFile | 50.000 | 50.000 | 0 |
| 未缓存输入 Token | 147,047.667 | 143,908.000 | -2.1% |
| 缓存读取 Token | 2,054,656 | 1,976,832 | -3.8% |
| 总提示 Token | 2,201,703.667 | 2,120,740.000 | -3.7% |
| 输出 Token | 18,503.333 | 19,373.667 | +4.7% |
| 运行错误 | 0 | 0 | 0 |

三次原始成功数：

```text
Baseline: 8/8, 6/8, 7/8
ZG:       6/8, 7/8, 7/8
```

三次耗时标准差：Baseline 39.924 秒，ZG 4.929 秒。ZG 本轮耗时更稳定。

## 工具轨迹

三次运行累计：

```text
Baseline: CodeSearch 86, ReadFile 150, Glob 2
ZG:       CodeSearch 95, ReadFile 150, Bash 2, Glob 1, memory_search 2
```

ZG 没有减少 ReadFile，并使 CodeSearch 增加 9 次。总提示 Token 仍降低约 3.7%，但输出 Token 增加约 4.7%。

## 失败分布

- Baseline：第 3 题失败 1 次，第 7 题失败 2 次。
- ZG：第 3 题失败 1 次，第 7 题失败 2 次，第 8 题失败 1 次。
- 第 3、7 题都涉及 File Ledger 和 Session 恢复的跨文件状态链，两组均出现波动。
- 全部运行均无认证、MCP、模型或工具执行错误。

## 结论

在这组复杂任务中，ZG 将平均耗时降低 5.8%、总提示 Token 降低 3.7%，并显著降低耗时波动；但没有减少 ReadFile，工具调用增加 5%，自动任务成功率还下降 4.2 个百分点。因此不能得出“ZG 全面提高复杂任务完成率”的结论。

更准确的结论是：ZG 对执行效率有小幅收益，但当前搜索结果大小和模型检索策略仍需调优。下一步应限制语义结果片段、减少重复 CodeSearch，并针对第 3、7、8 题检查完整轨迹后再复测。

## 限制

- 任务集只有 8 题，虽然重复 3 次，覆盖面仍有限。
- 模型自主工具选择有随机性，两组轨迹不完全相同。
- 自动判定只检查最终答案是否包含全部预设文件路径，不直接评价解释内容质量。
- Provider 缓存可能跨 Session 复用，因此缓存 Token 只作为运行观测值。
